# Cloud upload and listening Implementation Plan

> **For agentic workers:** REQUIRED SUB-SKILL: Use superpowers:subagent-driven-development (recommended) or superpowers:executing-plans to implement this plan task-by-task. Steps use checkbox (`- [ ]`) syntax for tracking.

**Goal:** Upload songs to a folder on the LWS hosting over FTP and play them back from any MuseHik laptop, inside a 10 GB/month traffic budget and a 30 GB storage cap.

**Architecture:** A new backend module `backend/modules/cloud/` talks FTP(S) with `basic-ftp`; every FTP access goes through one session object that confines paths to the configured folder and meters bytes into a shared `usage.json` on the cloud. Songs are fetched into a local LRU cache and streamed to the browser by the existing `streamFile`. The Angular app gets two pages (`cloud`, `cloud-upload`), a usage bar, and a Settings section.

**Tech Stack:** Node 26 (built-in `node:test`, `node:sqlite`), `basic-ftp` 6.x (dependency), `ftp-srv` 4.x (devDependency, tests only), Angular 22 + vitest.

**Spec:** `docs/superpowers/specs/2026-11-21-cloud-design.md`

## Global Constraints
- FTP only; nothing is installed on LWS. FTPS by default; plain FTP only when `allowPlainFtp` is true.
- Defaults: folder `music`, monthly limit **10 GB**, storage limit **30 GB**, cache **2 GB**, warning at **80 %**. GB = 1e9 bytes.
- Never touch a path outside the configured folder (reject `..`, absolute paths, backslashes, drive letters).
- The password never leaves `backend/data/cloud.json`: not in API responses, errors or logs.
- Month = local calendar month, key `YYYY-MM`. Limit message: `Cloud limit reached for <Month>. It resets on 1 <Next month>.`
- Cloud layout: `<folder>/library.json`, `<folder>/usage.json`, `<folder>/songs/<Artist - Title>.<ext>`.
- Follow existing module pattern: `routes.mjs` exports `handle(req, { res, json, cors })` returning true when handled.

## Review Focus
1. Two laptops write `library.json` at nearly the same time → neither song disappears for long: "Rebuild index" re-adds songs present in `songs/` but missing from the index (Task 3 test `rebuildIndex re-adds orphan files`).
2. Server unreachable / wrong password → a readable error, never a stack trace or the password (Task 2 test `connection errors never contain the password`).
3. Limit reached mid-upload-job → the job stops cleanly, finished songs kept, the rest reported as "limit reached" (Task 5 test `stops at the monthly limit`).
4. Stop pressed mid-file → no half file left in `songs/`, index unchanged for that song (Task 5 test `cancel leaves no partial file`).
5. Cache full → the least recently played file is removed, never the one being played (Task 4 test `evicts least recently used, keeps the newest`).

**Interfaces:**

### Task 3: Cloud index and shared usage counter

**Files:**
- Create: `backend/modules/cloud/store.mjs`
- Test: `backend/tests/cloud-store.test.mjs` (uses the Task 2 fixture)

**Interfaces:**
- Consumes: `openSession`, limits from Task 1.
- Produces: `withCloud(fn: (cloud) => Promise<T>, settings = loadSettings()): Promise<T>`; `cloud = { session, index(): Promise<Index>, addSong(entry): Promise<Song>, removeSong(id): Promise<boolean>, usedBytes(): Promise<number>, storedBytes(): Promise<number>, ensureRoom(bytes, { storage = false })  }`. At the end of `withCloud` (also on error) the session's bytes are added to `usage.json` for `monthKey()` by re-reading then writing it.
  `Index = { version: 1, nextId, songs: Song[] }`, `Song = { id, file, title, artist, album, duration, isrc, key, size, addedBy, addedAt }`. `addSong` and `removeSong` re-read `library.json` immediately before writing.
- Produces: `rebuildIndex(): Promise<{ added: number, removed: number }>` (songs in `songs/` without entry are added from the file name "Artist - Title"; entries without a file are dropped), `cloudStatus(): Promise<UsageSummary & { configured }>`, `lastIndex(): Index|null` (copy saved to `backend/data/cloud-library.json` after each read, used when offline).

- [ ] Step 1: tests: `addSong assigns increasing ids and keeps the other laptop's songs` (write an entry directly between two adds), `usage is added at the end of a session even after an error`, `ensureRoom throws LimitError past the month limit`, `ensureRoom with storage checks the 30 GB cap`, `rebuildIndex re-adds orphan files`.

### Task 5: Upload job

**Files:**
- Create: `backend/modules/cloud/upload.mjs`
- Test: `backend/tests/cloud-upload.test.mjs`

**Interfaces:**
- Consumes: `withCloud`, `checkStorage`, `LimitError`, `trackKey`/`sameLength` from `core/lib.mjs`, `parseFile` from `music-metadata`.
- Produces: `startUpload({ trackIds?: number[], paths?: string[] }): Job`, `getUpload(id)`, `cancelUpload(id)`, `activeUpload()`. `Job = { id, state: 'running'|'done'|'stopped'|'failed', total, done, bytesDone, bytesTotal, current, uploaded: Item[], skipped: Item[] (reason "Already on the cloud as ..."), failed: Item[] (reason) , error }`, `Item = { title, artist, file }`. One job at a time (`startUpload` throws if one is running). One FTP session per job; songs one by one: duplicate check against the index (ISRC, else key + length within 5 s), `ensureRoom(size, { storage: true })`, upload to `songs/<name>.part<ext>`, rename, `addSong`.
- Folder helpers: `scanFolder(path): Promise<FolderSong[]>` (audio files recursively, tags read), `pickFolder(): Promise<string|null>` (PowerShell `-STA` `FolderBrowserDialog`, topmost owner form).

- [ ] Step 1: tests: `uploads, then skips the same songs on a second run`, `stops at the monthly limit` (limit set just above one song: first uploaded, others failed with the limit message, job state 'done'), `cancel leaves no partial file`, `scanFolder lists audio in subfolders only`.
